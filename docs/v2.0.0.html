v2.0 is early alpha. It boots, joins a network, runs packages and updates itself, and it is still changing week to week. Anything here can move before 2.0 is called finished. For the settled system, v1.0 “Vela” is the MicroPython release and is documented separately.

Getting Started

What you need:

  • A Raspberry Pi Pico 2 or Pico 2 W — read Which Boards Work before reaching for an older Pico
  • A serial terminal at 115200 baud — PuTTY on Windows, minicom or screen on Linux and macOS

That is the whole list. v2 is a single firmware image rather than a set of files copied on top of something else, so there is nothing to install underneath it and no runtime version to match.

Installation

  1. Hold BOOTSEL and plug the board into USB. It appears as a drive named RP2350.
  2. Drag the .uf2 for your board onto it. Pick it from the Get page.
  3. The board reboots by itself. Open a serial terminal at 115200 baud.
After the first install you should not need that page again. The device updates itself over the network — see Updates.

First boot

A short setup runs once, the first time the device starts:

  1. You choose the root password
  2. A guest account is created, which accepts any password
  3. On boards with a radio, you are offered a WiFi connection

After that you land at the shell prompt. The setup does not run again unless the device is factory reset.

serial — 115200 baud
root@vela:/> ver
  RPCortex v2.0.0 "Vela II"
  pico2_w  RP2350  150 MHz  520 KB RAM

root@vela:/> help
  Type 'help <category>' for details, or 'help all' for every command.

help is the index. help all lists every command registered right now, which is the only listing that also includes commands added by a package you have loaded.

Which Boards Work

v2 builds for four boards. Two are usable today and two are not, and the difference is worth being blunt about.

BoardChipFilesystemSandboxStatus
Pico 2 WRP2350~1.8 MBYesPrimary target
Pico 2RP2350~1.8 MBYesSupported, no radio
Pico WRP2040NoneNoNot usable yet
PicoRP2040NoneNoNot usable yet
The original Pico and Pico W have no filesystem in v2. They carry 2 MB of flash, and v2 reserves 2 MB for firmware — one megabyte to run from, one as a staging slot an update is assembled in. That leaves nothing for storage. The image boots and the shell works, but nothing can be saved: no accounts, no settings, no packages. Fixing it means shrinking the reserve or giving RP2040 a different flash layout, and until that lands these two boards are for looking at rather than using. On an RP2040 board, v1.0 is the version to run.

What RP2350 adds beyond storage

  • A memory protection unit with regions to spare. That is what lets a package run unprivileged with its code, data, stack and heap each described separately. On ARMv6-M the regions are power-of-two sized and aligned to their own size, which would cost more RAM than an RP2040 has.
  • A hardware stack limit. A task that runs past the end of its stack faults at the instruction that did it, instead of quietly corrupting whatever the heap put below it and being blamed on something else later.
  • 520 KB of RAM against 264 KB — the difference between multitasking comfortably and counting bytes.

Boot Sequence

Every boot runs a short power-on check and prints what it found. Worth reading once, because it is also the first place a problem shows up.

boot
[:] [POST] Checking the machine...
[@] [POST] pico2_w  321 KB RAM, 321 KB free
[:] [POST] Mounting storage...
[@] [POST] Filesystem mounted  (1848 KB free)
[:] [POST] Reading the registry...
[@] [POST] 14 settings, 2 accounts
[?] [POST] The clock is not set. Use 'date set' or 'ntp sync'.
[@] [POST] System ready.

The prefixes are consistent everywhere in the shell, not just at boot:

PrefixMeaning
[:]Something is in progress
[@]It worked
[?]Worth knowing, not a failure
[!]Something failed

If the last run ended badly, the boot says so before anything else and names the command that was running. See Diagnostics.

Completion

Tab completes commands, then paths. It is case-adaptive: typing scr and pressing Tab finds Screenshot.jpg, and the completed word replaces what you typed rather than being appended to it, so the case ends up matching the file that actually exists. Names containing spaces are quoted for you.

The device filesystem is case-sensitive. /Packages and /packages are different directories. Completion adapting to case is a convenience for typing, not a change to how paths are matched.

History

history lists recent commands and the arrow keys recall them. History survives a reboot.

On meminfo and fragmentation. Free memory and usable memory are different numbers. A heap can report a large total free and still refuse a modest allocation, because the free space is in pieces rather than one run. meminfo prints the largest single block alongside the total, and that second number is the one that decides whether something will fit.

Clock speed

pulse set <mhz> changes the system clock now; pulse boot <mhz> makes it the value used at every boot. Lower is cooler and cheaper on power, higher is faster. The range that is actually safe is a property of the part, and pulse refuses values outside it rather than letting the board hang.

Two accounts exist after setup: root, an admin with the password you chose, and guest, which is not an admin and accepts any password. Admin is what gates the commands that can lose data — account changes, factory reset, firmware updates.

Running without a login

autonomy turns the login prompt off, so the device boots straight to a shell. That is the right setting for something installed in a box on a shelf and the wrong one for something on a desk with other people around. It is a registry setting like any other and can be turned back on the same way.

Registry & Settings

Every persistent setting lives in one registry, stored on the filesystem and read at boot.

CommandDoes
settingsA full-screen panel — the easy way

reg set <key> <value>Write one key

Keys are Section.Name. env with no argument shows the sections; env Settings shows one. The panel and the commands write the same store, so it does not matter which you use.

regreset restores settings. It does not remove accounts, files or packages — that is factoryreset.

Tasks & Multitasking

v2 runs tasks on both cores. The scheduler is cooperative: a task keeps the core until it yields, and it yields at defined points — printing, sleeping, waiting on the network, reading a file.

CommandDoes
psRunning tasks: pid, state, stack, CPU
ps -l...and the path each was started from
kill <pid>Ask a task to stop
bg <command>Run a command as a background task

What cooperative means in practice

A kill takes effect at the task's next yield point — somewhere it is not holding a lock or part-way through a write. That is a deliberate trade: a task that never yields cannot be killed, which is better than one that can be torn down in the middle of writing a file.

There is a backstop. A task that stops yielding entirely is noticed by a timer interrupt, and if the stall is inside a package the OS takes the call back without ending the task — a package command runs on the shell's task, so killing the task would take your session with it. From the shell's point of view the package simply returned. See The Sandbox.

Stack

ps reports how much of each task's stack has ever been used, measured from a fill pattern rather than estimated. A number close to its limit names the task to give more room.

Automation

CommandDoes
startup add <cmd>Run something at every boot
startup list | removeManage the list
task add <secs> <cmd>Run something every N seconds
task start | stopStart or stop the timer scheduler
service add <cmd>A long-running command, started at boot
watch [-n secs] <cmd>Re-run in the foreground until Ctrl+C

The three persistent ones differ in shape rather than power. startup runs once at boot and finishes. task runs on a repeating timer. service is for something that starts at boot and stays running — a web server, a logger.

A startup command that hangs will hang the boot. safeboot exists for exactly that: it restarts with no services, no startup commands and no packages, so there is always a way back to a prompt.

Scripting (.rps)

An .rps file is a list of shell commands with enough structure around them to make decisions. Run one with script <file> or run <file.rps>; runurl <url> fetches one and runs it.

Every line that is not a keyword is a shell line, run exactly as if typed — pipes, chaining and redirection included.

Variables

script.rps
set name world
echo hello $name

set n 0
inc n              # n is now 1
dec n              # back to 0

echo a literal $$  # prints: a literal $

$NAME expands anywhere in a line. An unset variable expands to nothing rather than to its own name, which is what makes if empty $x work before x has ever been set.

Conditions

script.rps
if exists /os/registry.json
  echo the registry is there
else
  echo fresh device
end

if eq $mode fast
  pulse set 250
end

if not empty $ssid
  wifi connect $ssid
end
TestTrue when
eq a ba equals b
ne a ba does not equal b
gt / lt a ba is greater / less than b
ge / le a bgreater or equal / less or equal
contains a bb appears inside a
exists paththe path exists
empty aa is empty
not <test>the inverse of any of the above
Anything else is a command, and its success is the condition. That is what makes if ping -c 1 example.com work without the language knowing anything about ping.

Loops

script.rps
set i 0
while lt $i 5
  echo pass $i
  inc i
end

break leaves the loop, continue starts the next pass, and stop ends the whole script.

Capturing output and asking questions

script.rps
capture lines wc -l /os/log.txt
echo the log has $lines

prompt name What should I call you?
echo hello $name

capture runs a command and puts its output in a variable. It sees exactly what a pipe would see, because it reuses the same machinery. prompt asks and waits.

Ctrl+C stops a running script at the end of the current line.

Saved networks are stored with their passwords in the registry. radio is a hard override that keeps every radio off regardless of other settings — the equivalent of aeroplane mode — and it survives a reboot until released.

The clock

There is no battery-backed clock, so the time is wrong after every power cycle until it is set. ntp sync sets it from the network and date set sets it by hand. ntp show reads the time without changing the clock, which is useful for checking the server is reachable.

USB Drive

download makes the board appear on your computer as a small removable drive, so files move by drag and drop instead of over the serial line.

shell
download                 # everything in /usb goes out
download report.txt      # or just these files

It works in both directions. Whatever is in /usb appears on the drive; anything you copy onto the drive lands in /usb when you leave the mode, and anything you delete there is deleted on the device.

The drive is a transfer area, not a view of the filesystem. It is a real FAT volume the device fills and empties, which is what makes it work with every operating system without a driver. Exposing littlefs directly would mean two filesystems writing the same flash with no idea about each other.
Windows caches removable-media directory listings aggressively. If a file you deleted still shows after re-entering download mode, the device is right and the cache is stale — the volume serial changes on each entry specifically to reduce this.

Packages

A package is a compiled .app file: real machine code, loaded and relocated at runtime. Not a script.

CommandDoes

pkgdisable / pkgenable <name>Stop or allow loading at boot

Installing puts the file in /apps and loads it. A package registers its commands when it loads, which is why help all shows them and help by category does not.

pkgdisable is the escape hatch for a package that misbehaves at boot: it stays installed but is not loaded, so there is no need to remove and reinstall it to test a theory.

The Sandbox

On RP2350 a package runs unprivileged, with the memory protection unit describing exactly five regions it may touch: its code, its data, its call veneers, its stack and its heap. Everything else in the machine is denied — the OS's own tables, the peripherals, and flash.

What that buys

  • A package cannot reach outside itself. A bad pointer is refused by hardware rather than corrupting something a minute later.
  • Every pointer a package hands the OS is range-checked against the regions that package owns. A package cannot ask the firmware to read or write memory on its behalf that it could not touch directly.
  • Its own stack and heap. A package running out of memory runs out of its memory, and the message says so instead of looking like the device being out of RAM.

What happens when a package misbehaves

The package...Costs you
Uses a bad pointerThe command. A report names the package and the offset, and the shell carries on.
Stops responding entirelyThe command. The call is taken back at a timer interrupt; the session survives.
Asks for something that does not existNothing. The call is refused and an error returned.
Runs out of its own stackA restart, with a report naming it.
Why a stack overflow still restarts. An exception pushes its frame below the stack pointer, so a stack with nothing left has nowhere to put one. The frame is never written, and a frame that was never written cannot be redirected somewhere survivable. That is the architecture rather than a missing feature, and the report still names the package and the fault.

On RP2040 none of this applies: there are not enough protection regions to spare, so packages there run with the OS's own privileges.

Writing Packages

Packages are written in C or C++ and built on a computer with the SDK, then copied to the device. The package development guide is the long version; this is the shape of it.

hello.c
#include "rpc_app.h"

static int cmd_hello(int argc, char **argv) {
    fw_printf("hello from a package\n");
    return 0;
}

int app_main(int arg) {
    rpc_register_command("hello", "say hello", cmd_hello);
    return 0;
}

app_main runs when the package loads and is where commands are registered. Everything the OS offers is reached through fw_* functions — around 166 of them, covering printing, memory, files, directories, tasks, networking, TCP, HTTP, GPIO, I2C, SPI, PIO, ADC and a full-screen text interface.

A sandboxed package cannot branch into the firmware, because flash is not reachable from unprivileged code. Every fw_* call is therefore a supervisor call underneath. The SDK builds that for you; it matters only in that an ABI call is not free, so a tight loop calling one is worth restructuring.

Four packages ship with source as examples: httpd, websearch, speedtest and dht. They are ordinary packages with no privileges yours does not have.

Updates

The device updates itself over the network. There is no need to return to the installer page after the first flash.

shell
update check      # is there a newer version?
update            # download and install it
update channel beta | stable

An update downloads the new image to the filesystem, copies it into a staging slot, and only then writes it over the running firmware. Source and destination are the same flash chip, so the staging step is what makes it safe: by the time the firmware region is erased, the new image is somewhere the erase does not touch.

Do not power the board off during the final write. The staging slot means an interrupted download is harmless, but an interrupted write needs a BOOTSEL reflash.

The beta channel gets pre-release builds. On an early-alpha release that distinction matters less than it will later, but it is there.

After a crash

The next boot leads with what happened:

boot
[!] [Crash] Last run stopped while running 'shell' (pid 3, core 0).
   Command   : havoc stack
   Reached   : STKOF stack overflow in havoc+1b28   <- it stopped here
   Yields    : 118644 before it stopped
   Stack     : 1952 of 8192 bytes used

That record is written continuously into memory the reset does not clear, so it survives whatever took the device down. logdump has the lines leading up to it, from before and after the reboot both.

A watchdog restart and a fault are different things, and the report says which. A fault names an instruction. A watchdog restart means something stopped responding, and the Reached line names the last checkpoint the code got to.

compat

compat probes the board and reports what is actually present rather than what the build assumed — radio, Bluetooth, the temperature sensor, the number of protection regions, the clock range. It is the first thing to run when something is missing that you expected to be there.

Recovery

Four ways back, in increasing order of what they cost.

CommandDoesLoses
safebootRestart with no services, startup commands or packagesNothing

pkgdisable <name> is worth knowing alongside these: it stops one package loading at boot without removing it, which is usually enough to get back to a working shell without losing anything.

If none of those get you a prompt, hold BOOTSEL and reflash. That always works, because it does not depend on anything on the device being correct.

Moving from v1

v2 is a rewrite in C++, not an upgrade of v1. The shell is deliberately familiar and almost everything underneath is different.

 v1 “Vela”v2 “Vela II”
Written inMicroPythonC++
Ships asFiles on top of a runtimeOne firmware image
PackagesPython source, .pkgCompiled .app
Package isolationNoneUnprivileged, hardware-enforced
BoardsRP2040, RP2350, ESP32-S3RP2350 (RP2040 boots, no storage)
Scripts.rps.rps, same language

Scripts carry over. The .rps language is the same, and capture deliberately sees what a pipe would, so lines like capture n wc -l file behave identically on both.

Packages do not. A v1 .pkg is Python source and there is no Python in v2. The four that ship with the SDK have been rewritten in C; a package of your own needs the same treatment.

The two cannot share a board. v2 replaces the firmware entirely, so installing it removes MicroPython and everything stored under it. Save anything you want to keep first.

The full comparison covers why the rewrite happened.

Known Limitations

The honest list, as of v2.0.0.

  • RP2040 boards have no filesystem. The firmware reserve is their entire flash. See Which Boards Work.
  • A package that exhausts its own stack restarts the device. Every other package fault is contained. See The Sandbox.
  • No Python. Packages are compiled. That is the point of v2, but it is a real loss of convenience against v1.
  • The package catalogue is small. v1's twenty packages have not all been ported. That work is the main thing between v2 and parity.
  • No ESP32 port. v1 runs there; v2 does not, yet. The core is portable, the context switch, storage and network layers are not.
  • No SD card support. It needs a driver.
  • help by category does not list every command. The categories cover the common set; help all is the complete list.
  • Cooperative scheduling. A task that never yields cannot be killed from the shell. The timer backstop covers packages, not firmware.
  • Early alpha. Things move. If something here does not match the device, the device is right — and it is worth saying so.
